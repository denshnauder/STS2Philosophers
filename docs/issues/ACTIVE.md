# 活动问题队列

> 本文件只保存尚未闭环的问题。Codex 每次开始仓库开发任务时必须先读取本文件。
> 已解决问题不得继续保留在这里，必须迁移到 `docs/issues/resolved/`。

## 状态

- `待处理`：已记录，尚未开始。
- `处理中`：正在定位、修改或测试。
- `待验证`：代码修改已完成，但仍缺少足够验证，或需要游戏内/用户确认。
- `阻塞`：缺少用户决策、外部资源、环境条件或无法安全继续。
- `已解决`：不允许留在本文件；确认解决后立即归档。

## 执行原则

1. 优先继续 `处理中` 和 `待验证`，再处理 `待处理`。
2. 一次代码修改完成不等于问题解决；应继续执行与风险相称的测试、构建、日志检查、部署或其他验证。
3. 除非出现真正需要用户决策、外部资源或人工游戏验收的阻塞，否则不要在中间步骤停下等待新的指令。
4. 每个问题持续维护：现象、目标、状态、根因、已做修改、验证结果、下一步。
5. 修复过程中发现独立的新问题时，新增独立问题项，不把多个问题无限堆进同一条。
6. 问题确认解决后，将完整记录迁移到 `docs/issues/resolved/YYYYMMDD ISSUE编号 问题简称.md`，并从本文件删除。

## ISSUE 001 建立自然的 ChatGPT 到 Codex 持续开发工作流

**状态：** 待验证  
**优先级：** 高

### 问题

目前 ChatGPT、Google Drive 项目资料和本地 Codex 开发之间仍然比较割裂。希望用户只需要提出问题或修改方向，Codex 后续能够读取固定的问题入口，持续定位、修改、测试和迭代，直到问题真正解决，而不是每一轮都重新解释上下文和手动下指令。

### 期望方向

- 建立固定、唯一的 Codex 活动问题入口。
- Codex 开始 STS2Philosophers 开发任务时自动读取活动问题。
- Codex 持续推进“定位 → 修改 → 测试 → 复查”，不因完成一次代码修改就默认结束。
- 问题具有明确状态，并在工作过程中持续更新。
- 尽量用自动测试、构建、日志或游戏内验收作为闭环依据。
- 已解决问题从活动列表迁移到归档，活动列表只保留仍需处理的内容。
- 归档保存根因、最终修复、验证方式和涉及文件，形成可搜索的项目技术记忆。
- 尽量减少用户在 ChatGPT、Drive、Codex、本地仓库之间复制粘贴。

### 已完成

- Google Drive 已建立 `08问题闭环`，包含活动问题与 `已解决` 归档目录。
- GitHub 仓库已建立本活动问题队列。
- 正在把启动读取、持续推进、验证和归档规则加入根目录 `AGENTS.md`。

### 验证条件

下一次使用 Codex 处理本仓库时：

1. Codex 能主动读取本文件；
2. 能识别未解决问题和状态；
3. 在没有真实阻塞时持续推进而不是只做一步；
4. 完成后能按规则迁移归档。

满足后将 ISSUE 001 迁移到 `docs/issues/resolved/`。
