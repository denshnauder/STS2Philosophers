# 活动问题队列

> 本文件只保存尚未闭环的问题。Codex 每次开始仓库开发任务时必须先读取本文件。
> 已解决问题不得继续保留在这里，必须迁移到 `docs/issues/resolved/`。

## 状态

- `待处理`：已记录，尚未开始。
- `处理中`：正在定位、修改或测试。
- `待验证`：代码修改已完成，但仍缺少足够验证，或需要游戏内/用户确认。
- `阻塞`：缺少用户决策、外部资源、环境条件或无法安全继续。
- `已解决`：不允许留在本文件；确认解决后立即归档。

## 执行原则

1. 优先继续 `处理中` 和 `待验证`，再处理 `待处理`。
2. 一次代码修改完成不等于问题解决；应继续执行与风险相称的测试、构建、日志检查、部署或其他验证。
3. 除非出现真正需要用户决策、外部资源或人工游戏验收的阻塞，否则不要在中间步骤停下等待新的指令。
4. 每个问题持续维护：现象、目标、状态、根因、已做修改、验证结果、下一步。
5. 修复过程中发现独立的新问题时，新增独立问题项，不把多个问题无限堆进同一条。
6. 问题确认解决后，将完整记录迁移到 `docs/issues/resolved/YYYYMMDD ISSUE编号 问题简称.md`，并从本文件删除。

## ISSUE 001 建立自然的 ChatGPT 到 Codex 持续开发工作流

**状态：** 待验证  
**优先级：** 高

### 问题

目前 ChatGPT、Google Drive 项目资料和本地 Codex 开发之间仍然比较割裂；同时 Codex 额度经常在工作中途耗尽，导致任务停在半途，新窗口不能立刻从准确状态继续。

### 期望方向

- 建立固定、唯一的 Codex 活动问题入口。
- Codex 开始 STS2Philosophers 开发任务时自动读取活动问题。
- Codex 持续推进“定位 → 修改 → 测试 → 复查”，不因完成一次代码修改就默认结束。
- 问题具有明确状态，并在工作过程中持续更新。
- 每完成一个可独立验证的小阶段就及时提交，并把“已做到哪里、下一步是什么、失败点是什么”写回活动问题。

- 已解决问题从活动列表迁移到归档，活动列表只保留仍需处理的内容。

## ISSUE 002 赐福强度与思想约束失衡

**状态：** 待处理  
**优先级：** 高

### 问题

当前赐福的正面效果普遍较强，而对应的行为限制、机会成本、违背代价不明显；不同思想路线之间的净收益差异也较大。两者本质上是同一个问题：目前更多是在给“有主题的强力遗物”，还没有稳定形成“接受一种思想就必须承担一种行为约束”。

### 期望方向

- 不先做逐件数值微调，先建立统一的设计预算和约束框架。
- 每条路线至少明确：行为要求、正面回报、机会成本/违背代价、适配构筑、最坏滥用方式。
- 平衡比较应看“为了拿到收益需要改变多少正常打法”，而不只看遗物提供了多少数值。
- 允许部分思想更强，但必须对应更苛刻、更窄或更有风险的实践条件。
- 后续新增交叉/转派机制时，不能让玩家只挑各流派最强收益叠加。

### 验证目标

形成可自动或半自动检查的平衡基准，使明显失衡能在大量人工爬塔之前被筛出。

## ISSUE 003 人工验收负担过高且路线难以记忆

**状态：** 待处理  
**优先级：** 高

### 问题

现有 6 条路线、12 件遗物已经超过用户能轻松记忆和逐条完整爬塔验收的规模。用户没有足够时间通过大量实际游玩判断什么好用、什么不好用，也难以清楚记住“路线 → 人物 → 遗物 → 效果”的对应关系。

### 期望方向

- 把人工游戏测试从“主要验证方式”降为“最终体验抽查”。
- 增加可批量执行的机制模拟、场景测试或统计输出，尽量自动发现过强、过弱、触发率异常和死条件。
- 为所有思想路线建立游戏内或开发侧的清晰总览：人物、思想关键词、当前赐福、核心约束、后继/可能分支。
- 设计上减少必须背诵的隐藏关系，让事件 UI 本身解释“为什么这个人物现在出现、他和你当前思想是什么关系”。
- 后续讨论新的路线时优先使用统一的路线卡片/矩阵，而不是依赖记忆。

### 验证目标

用户无需记住全部内部结构，也能在游戏中理解当前思想状态；开发阶段无需完整跑完每条路线即可筛掉大部分机制和平衡问题。

## ISSUE 004 线性路线应改为随机邀请、交叉争鸣与第三层发展

**状态：** 处理中
**优先级：** 最高

### 问题

当前结构是第一层固定孔子/墨子/老子，选定一个根基后第二层只出现唯一固定后继，导致思想系统实际上是“选一条科技树一直升级”。这与项目期待的“思想之间发生碰撞、交叉、争鸣、修正甚至转派”不一致；同时第三层尚未实现。

### 期望方向

- 第一层思想家不再全部写死展示，改为从合法候选池随机出现若干邀请者。
- 随机不是纯 RNG，应结合角色、牌组、行为、已有思想状态或权重，使“思想家注意到玩家”有可解释性。
- 第二、第三层不再只有唯一纵向后继，而应允许出现至少三类关系：继承/深化、同题争鸣/修正、跨派邀请/转向。
- 第三层必须成为正式系统的一部分，用于会通、决裂、极端化、反驳或更高层次的思想重构，而不是简单再升级一次遗物。
- 不允许玩家无成本叠加多个流派的最优收益；转派、会通或接受对立思想应产生替换、冲突、代价或新的约束。
- 随机候选池可以同时承担部分强度平衡：强势赐福降低出现概率或提高青睐门槛，但不能用随机性掩盖根本数值失衡。

### 设计前置问题

- “思想关系”应成为图而不是树：需要定义人物之间的关系类型和可转移边。
- 需要决定第三层的功能：结论、会通、决裂还是一次最终论辩。
- 需要定义思想家青睐玩家的可解释条件，以及 UI 如何向玩家展示这些原因。

### 验证目标

一局游戏中的思想经历具有不确定性与叙事性：玩家可能坚持原说，也可能被新的思想吸引、修正、反驳或转向；不同局不再稳定走同一条固定路线。

### Phase 1 阶段结果

- 已审计第一层事件入口、第二层固定后继、局内存档字段、12 件遗物状态与青玉佩到熊掌的德继承；结构说明见 `DEVELOPMENT.md` 与 Obsidian 活动记录。
- 已建立 `CurrentDoctrine`、`ThoughtImprints`、`ActBehaviorStates`、`GeneratedCandidates` 的最小局内状态；思想印记目前只记录历史，不影响战斗。
- 第一层已改为孔子、墨子、老子中等概率随机展示两位；候选在进入事件前写入本局存档，载入后复用，拒绝路径保留。
- 已加入 `ThinkerProposal` 配置雏形，六个第一层提案从 `config/thinker_proposals.json` 读取；未实现的资格规则与共鸣标签明确留空。
