# 项目设计边界

## 三分钟摘要

- **当前结论：** 设计先于代码，但设计结论必须同时承担玩家操作、实际取舍、失败恢复和正式制作成本。
- **玩家流程：** 每个交付 Issue 完成一个可独立说明的玩家循环；部署后即可进入后续开发，试玩反馈另开 Issue。
- **核心取舍：** 复用基础设施，不让已有代码倒逼设计；保留历史证据，不让旧任务状态覆盖 Linear。
- **界面与素材成本：** 默认只使用原生界面、既有图标与少量静态图。柏拉图守灯与旅人继续只作设计实验。
- **已完成：** 当前设计、玩家事实、实现事实和研究归档已分入口。
- **准确下一步：** 对应人物任务只更新其唯一当前入口和确有必要的支撑材料。

## 不可混淆的证据层

1. 用户锁定的项目方向与限制。
2. 研究来源、解释争议与游戏创作之间的边界。
3. 候选设计及其反例。
4. 已实现并通过相关自动检查的内容。
5. 已完成构建、安全部署并可由玩家进入的内容。
6. 玩家之后提出的界面、文案、平衡与体验反馈。

自动检查只能证明实现符合已写规则，不能证明思想表达或乐趣成立；玩家尚未试玩也不能把已经安全部署的交付保持在未完成状态。

## 制作底线

- 优先复用战斗、卡牌、遗物、奖励、地图和标准事件界面。
- 不把纯文字原型成立等同于正式制作可行。
- 不默认 AI 美术能通过风格、来源、版权和可读性审查。
- 存档、公共状态、迁移和不可逆操作继续按高风险变化处理。

详细规则见 [美术与制作约束](../../ProductionConstraints.md) 与仓库根目录 `AGENTS.md`。
